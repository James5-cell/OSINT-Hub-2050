# 基于《Open Source Intelligence Methods and Tools》的项目评估

评估日期：2026-10-03。参考 Nihad A. Hassan、Rami Hijazi 的 2018 年著作，并对照当前项目代码和数据库。阅读覆盖全书目录、九章主题、关键方法段落及总结；不是对每一个旧工具的逐项验证。下文书籍页码指书内印刷页码，通常不同于 PDF 页序。

## 核心判断

建议定位为：**帮助普通人从一个问题出发，找到合适的公开来源，并学会判断查到的资料。**

教育与工具可以在同一条路径中完成：明确问题 → 选择来源 → 按步骤查询 → 核实结果 → 留下有来源的结论。工具负责降低操作门槛，教育负责解释为什么这么查、结果能证明什么。

项目自己的 database 应是“资源与方法数据库”，而不是收集个人资料的数据库，也不是包办全网答案的搜索引擎。继续采用本地结构化数据、构建时生成索引、浏览器查询即可；现有规模不需要接入 Meilisearch。

## 全书对项目的启发

| 书籍主题 | 值得迁移的概念 | 项目应补充的内容 |
| --- | --- | --- |
| 第 1 章：OSINT 的发展 | 原始数据、整理后的信息与经过判断的结论有区别；公开不等于可信 | 入门短课：什么是线索、什么是证据、什么仍然未知 |
| 第 2 章：调查准备 | 记录、时间线、书签、翻译与研究环境也影响工作质量 | 简单查证记录模板；按任务提供必要准备，专业配置放进进阶内容 |
| 第 3 章：非通用搜索覆盖的网络内容 | 有些资料需要进入数据库的查询表单，普通搜索无法完整覆盖 | 解释“为什么要查登记库、档案库、学术库”；不要把 deep web 等同于 dark web |
| 第 4 章：搜索方法 | 关键词变体、搜索限制、历史网页、媒体和文档查证 | 查询模板、姓名变体提示、来源追溯、新闻与视频查证入口 |
| 第 5 章：社交媒体 | 账号、帖子、图片、互动是不同线索，查询条件不同 | 公开账号核实流程，解释同名、转载和候选账号的局限 |
| 第 6 章：人物与公开记录 | 姓名、用户名、邮箱等入口不同；资料覆盖依赖地区与数据库 | 按真实输入条件推荐；区分公开平台、原始记录与聚合索引 |
| 第 7 章：地图 | 地图、影像、现场线索需要交叉比较 | 图片地点核实短案例，明确影像拍摄时间与观察时间 |
| 第 8 章：网站背景 | 官网资料、历史版本、注册资料与技术信息可以串联 | 先教网站身份与历史核实，再提供进阶技术调查 |
| 第 9 章：完整工作过程 | 找来源、收集、处理核实、分析关联、呈现发现 | 搜索之外，补齐结果解释、证据组织和简短输出 |

书中第 9 章印刷第 343 页明确列出五个阶段；“先明确问题”是适合本项目新手用户的额外设计，不是原书的第六个阶段。第 1 章第 3–5 页讨论数据到情报的层次，第 4 章第 129 页讨论关键词，第 6 章第 261–264 页讨论人物查询入口。

书籍出版于 2018 年。应借鉴方法，逐项核对拟采用的工具与操作；旧平台、旧搜索语法、覆盖范围及法律表述不能直接成为今天的产品承诺。

## 当前项目有哪些基础，缺口在哪里

当前生成库包含 123 个有效资源，10 类输入入口和 29 条较完整的资源使用指南；已有 11 套完整中英双语工作流，包含目的、操作、观察结果、常见误区和准备说明。因此，不需要从零写课程，也不应把原有流程再复制成另一套笔记。

首页、搜索与学习页已建立“先问问题、再选资源”的方向，但学习页主要是原则说明；用户完成一次查询后，仍缺少结果判断练习与记录工具。

此前人名只出现两条，是只覆盖少量有使用指南的资源。扩大匹配后，人名入口目前返回 52 条相关资源，但这不代表 52 个资源都能接受姓名查询。当前数据将“调查对象”与“工具接受的输入”混在一起，这是下一步最重要的改进。

例如，用户名枚举工具需要用户名，图片检索需要图片，关系分析软件通常需要已有线索。研究环境、加密或隐私工具也可能有 person 标签，但不能因此排在人名查询的直接来源前面。

此外，具体目标和地区筛选主要依赖 guide 字段。没有补充指南的资源可能被筛掉，即使资源本身相关。因此，不能只改排序或多加关键词，还需要补齐能力与覆盖元数据。

现有双语内容也存在展示事实错误：学习页链接写“完整查证流程（英文）”，README 和产品文档称流程主要为英文；实际加载器支持完整繁体中文流程。这应作为后续修正项。

## 教育功能：让用户完成一次小任务

### 六个轻量模块

每个模块采用“一个概念 + 一个例子 + 一次选择或操作 + 简短反馈”，提供约 3–5 分钟的学习目标，不承诺每个人都能在固定时间完成。

1. **我究竟想知道什么？** 把“查一家公司”改成“确认注册名称、所在地与登记状态”。先限定问题，避免无限扩张。
2. **我手里有什么线索？** 区分姓名、用户名、邮箱、域名、图片与公司编号。教用户选择正确入口。
3. **怎样组合关键词？** 使用姓名变体、语言、单位或地区线索，以及适用于指定搜索引擎的查询模板。
4. **怎样读结果？** 同名不等于同一人；搜索无结果不等于不存在；页面更新时间不一定是事件发生时间。
5. **怎样交叉核实？** 回到原始来源，判断多篇文章是否只是转载同一材料，区分证据、推测与冲突。
6. **怎样留下可以复查的结论？** 记录来源链接、获取时间、关键观察、未解决问题与下一步。

先把现有公司、人物公开职业资料、图片查证和网站背景四套流程提炼成任务卡。专业技术调查和研究环境配置保留进阶入口，避免新手开始查询前必须阅读整章准备内容。

### 用练习代替继续堆解释

- 两个同名账号，单位不同：能否判定是同一人？反馈应说明还缺什么证据。
- 三篇报道引用同一份新闻稿：是否算三个独立来源？让用户追溯源头。
- 一张旧照片被配上新事件说明：图片来源和事件背景分别如何核实？
- 公司登记页面：哪些字段能确认法律主体，哪些不能证明经营质量或可信度？

练习使用虚构对象或公开机构资料。评价重点是用户能否连接问题、来源与证据，不是点击了多少网站。

## 工具功能：解释输入、输出和下一步

每条资源应能回答六句话：

1. 你需要先有什么信息？
2. 它可以回答哪个问题？
3. 你会得到什么类型的结果？
4. 第一步怎么操作？
5. 哪些结果需要人工核实？
6. 得到结果之后下一步做什么？

搜索卡片默认只展示“推荐原因、所需输入、预期结果”。展开后再展示操作示例、访问条件、地区覆盖和误判提示。这样补充解释不会把界面重新变成笔记。

| 资源示例 | 输入条件 | 应如何解释结果 |
| --- | --- | --- |
| 公开职业平台 | 姓名，最好同时有单位或地区 | 找到候选职业资料；不能只凭同名确定身份 |
| WhatsMyName 类工具 | 已知用户名 | 找到候选账号位置；须人工检查账号内容与关联线索 |
| TinEye 类工具 | 图片或支持的图片链接 | 查找相似或已有副本；结合来源页核实，未找到不等于原创 |
| 公司登记数据库 | 公司名称或登记编号，以及相应地区 | 确认登记主体与记录；不能据此直接判定信誉 |
| 关系分析软件 | 已整理的多个线索 | 帮助组织关联；图中连线本身不是证据 |

这些是能力分类示例，不是本次对各服务现行功能的完整审计。上线具体操作前，应检查对应官方说明。

### 人名搜索应怎样变化

用户输入“人名”后，先提供“公开职业资料”“公开记录”等目标，并给出一个简短提示：补充单位、地区或用户名可以帮助排除同名。

结果按照作用解释：

- **可以从姓名开始**：直接人物相关公开来源，按地区与目标排序。
- **需要补充线索**：用户名、邮箱、图片或公司名称入口；明确所需条件。
- **用于整理与分析**：用户已经收集资料后使用。
- **研究准备**：放在适当的辅助区域。

完整目录仍保留所有相关资源。准确推荐意味着用户理解工具能做什么，而不是把所有 person 标签的资源平铺，或再次只剩两条人工指南。

### 增加一个简单的查询模板功能

用户选择问题、填写已有线索，系统生成可复制的查询建议，并解释用途。例如：

```text
"示例姓名" "示例单位"
"示例公司" site:example.org
"示例公司" filetype:pdf
```

示例中的对象和域名仅用于说明，实际查询应替换成用户线索。引号、排除词及 site 查询可参考 [Google 搜索帮助](https://support.google.com/websearch/answer/2466433)；filetype 可参考 [Google 搜索运算符文档](https://developers.google.com/search/docs/monitor-debug/search-operators)。模板必须标明适用引擎，不把同一语法当成所有数据库通用。

模板能改善表达和范围，不能保证结果真实或搜索覆盖完整。Google 也明确说明 [site 查询结果不一定完整](https://developers.google.com/search/docs/monitor-debug/search-operators/all-search-site)。

## 数据库需要怎样调整

保留现有构建和本地索引机制，补充少量明确字段，避免构造庞大的分类体系：

| 数据维度 | 作用 |
| --- | --- |
| 资源类型 | 区分官方数据库、公开平台、搜索引擎、聚合索引、软件和方法 |
| accepted_inputs | 真正接受哪些输入，如姓名、用户名、公司编号、图片 |
| capabilities / tasks | 能完成哪些具体查询任务 |
| output_types | 结果是候选账号、登记记录、历史网页还是元数据 |
| 任务关系 | 直接查询、需要补充线索、分析或准备；按任务描述，不能全局固定 |
| coverage / access | 地区、语言、登录、安装与费用条件；未知不能默认为不可用 |
| interpretation / next_step | 如何读结果、常见误判、下一步 |
| verification | 官方说明链接、最后核对日期及核对范围 |
| lesson / workflow | 关联短教程和已有完整流程 |

同一资源可以有多个能力记录，每个记录对应不同的输入、任务和条件。目标筛选使用能力数据，避免以“有没有完整文章”判断资源是否相关。搜索结果应解释匹配理由；模型或规则推断的弱关联不要包装成已验证的支持能力。

避免使用“确认账号”“绝对准确”“无痕”等没有证据支撑的措辞。结果页面返回匹配项，通常不等于已经完成身份核实。项目价值在于帮助用户正确使用公开资料，不宜承诺凭几个关键词得到确定答案。

## 应增加哪些内容，按什么顺序

### 第一阶段：修正推荐逻辑，优先于增加资源

1. 为人名、公司、图片这三个常用入口补齐真实输入、输出和任务关系。
2. 修正目标与地区筛选对少量 guide 的依赖，清楚显示覆盖未知。
3. 调整工具说明中的过度承诺，以及双语流程的错误标识。
4. 加入简单查询模板和“结果如何判断”提示。

验收：姓名查询优先展示能从姓名开始的来源；用户名和图片工具显示补充条件；改变目标不会只因缺少文章而丢掉适用资源。

### 第二阶段：补齐教育闭环

1. 把现有四个核心流程改编成短任务卡与练习，保留原流程作为深入阅读。
2. 提供轻量查证记录，可本地复制或导出：问题、来源、时间、观察、限制、结论、下一步。
3. 优先补新闻与说法核实、视频来源与背景、文档与学术资料；分别核对资源后再发布。
4. 评估电话号码入口：现有资源已有 phone 标签，但当前搜索没有独立入口；应先明确可支持的任务和地区，避免笼统承诺可识别任何号码持有人。

验收：新手能完成一次查询，并说清楚哪些证据支持结论、哪些仍无法确定。

### 第三阶段：根据真实需求扩展

进阶技术调查、复杂时间线、监测与关系图可逐步补充。暂不把暗网导航、完整匿名环境、庞大课程系统或复杂案件管理作为默认入口；这些会重新提高使用门槛。

## 建议的页面结构与维护方式

首页突出“你想查什么”；查询结果包含直接资源、简短操作和判断提示；学习页提供少量短课和案例；完整目录承载全部资源与高级筛选。已有工作流继续承担深入阅读。

新增资源的门槛应是“能回答哪个问题、需要什么输入、有何限制”，而不是“书里出现过这个链接”。先人工核对高频入口，再持续维护核对日期、不可用状态与替代来源。书中的方法可以长期参考，具体服务需要持续更新。

本次输出为评估文档，没有改动页面或搜索代码，也没有逐一核验全部 123 个外部服务。
